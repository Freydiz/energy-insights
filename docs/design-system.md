# Energy Insights design system

This document defines the design rules for Energy Insights. It is a small product contract, not a component-library specification.

## Source of truth

`src/app/globals.css` is the single source of truth for actual design token values. This document describes token meaning and usage without duplicating color values.

Before changing the interface:

1. Reuse an existing semantic token or Tailwind utility when it expresses the intended role.
2. Add a token only when a value has shared product meaning or must change consistently across the application.
3. Add a reusable component only after a concrete, repeated use case exists.

## Visual direction

Energy Insights is a modern, minimal, Scandinavian, data-focused SaaS dashboard. The interface should prioritize clarity, trustworthy data presentation, restrained color, generous whitespace, and accessible interaction over decoration.

The current design is light-mode only. Do not add or activate dark-mode styling until a complete dark palette and interaction states have been reviewed.

## Semantic colors

Use semantic utilities generated by Tailwind's `@theme inline` mapping. Do not use raw hex values or Tailwind palette colors in product components.

| Token | Intended use |
| --- | --- |
| `background` | Application canvas and page background |
| `surface` | Cards, panels, and control surfaces |
| `foreground` | Primary text and high-emphasis content |
| `muted-foreground` | Secondary text, metadata, and supporting copy |
| `primary` | Primary actions, selected states, and links where appropriate |
| `primary-hover` | Hover state for primary actions |
| `primary-active` | Pressed or active state for primary actions |
| `primary-foreground` | Text and icons displayed on primary backgrounds |
| `accent` | Energy-data highlights, chart marks, and non-text emphasis |
| `border` | Decorative card borders and separators |
| `border-strong` | Form controls and boundaries that must remain clearly perceivable |
| `focus` | Keyboard focus indicators |

Accent teal does not meet WCAG AA contrast for normal-sized text on white. Use it for graphical emphasis, sufficiently large text, or non-text UI that meets the relevant contrast requirement. Do not use it for small body text or white-on-accent buttons.

The standard border is intentionally subtle and decorative. Use the strong border when the boundary is required to identify an interactive control.

## Semantic tokens and Tailwind utilities

Semantic tokens communicate product meaning and should be used for color:

```text
bg-background bg-surface text-foreground text-muted-foreground
bg-primary text-primary-foreground border-border outline-focus
```

Tailwind utilities communicate structure and should be used directly for layout, spacing, sizing, responsive behavior, typography, and state variants:

```text
flex grid gap-4 md:gap-6 px-4 md:px-8 max-w-7xl rounded-xl
text-sm font-semibold hover:* focus-visible:* disabled:*
```

Avoid arbitrary values unless they represent genuinely one-off geometry, such as calculated chart dimensions. Repeated utility combinations should first be colocated with the feature; extract them into a component only when repetition or a shared behavioral contract makes the abstraction useful.

## Spacing and layout

Use Tailwind's default 4px spacing scale and default breakpoints. Do not introduce custom spacing or breakpoint scales.

- Maximum content width: `max-w-7xl` (1280px).
- Page padding: `px-4` on mobile and `md:px-8` on larger screens.
- Card padding: `p-4` on mobile and `md:p-6` on larger screens.
- Card and grid gaps: `gap-4` on mobile and `md:gap-6` on larger screens.
- Section spacing: `space-y-8` on mobile and `md:space-y-12` on larger screens.
- Card radius: `rounded-xl` (12px).

Layouts are mobile-first. Unprefixed utilities define the mobile experience. Use `md:` for density changes such as padding and type size, and reserve `lg:` for structural changes such as multi-column dashboard layouts.

## Typography

Geist Sans is the global interface typeface. Geist Mono is reserved for content where a technical monospace treatment improves comprehension, such as raw timestamps, identifiers, or code.

Use Tailwind's existing typography scale rather than creating a custom type scale:

- Page title: `text-3xl/9 font-semibold tracking-tight md:text-4xl/10`.
- Section title: `text-xl/7 font-semibold`.
- Card title: `text-base/6 font-semibold`.
- Body: `text-base/6`.
- Label: `text-sm/5 font-medium`.
- Supporting text: `text-sm/5 text-muted-foreground`.
- KPI value: `text-3xl/9 font-semibold tabular-nums md:text-4xl/10`.

Use `tabular-nums` for numerical dashboard values so changing values remain visually aligned. Do not use Geist Mono for all numerical data by default.

## Accessibility

- Meet WCAG AA contrast for text, controls, states, and meaningful graphics.
- Every interactive element must have a visible `focus-visible` indicator. Never remove the browser outline without an equally visible replacement.
- Do not rely on color alone. Pair color with text, icons, patterns, line styles, or direct labels.
- Data visualizations must provide an equivalent textual or tabular representation when the graphic carries essential information.
- Use semantic HTML and native controls before recreating behavior with generic elements.
- Controls must expose hover, active, focus, disabled, selected, invalid, and loading states when those states apply.
- Respect `prefers-reduced-motion`; motion must not be required to understand content or state.
- Inputs require visible labels. Placeholder text is not a label.

## Architectural decision log

### CSS-first Tailwind configuration

Design tokens live in global CSS and are exposed with Tailwind CSS 4's `@theme inline`. No JavaScript Tailwind configuration or token package is needed for a single application.

### Semantic runtime variables

Concrete light-mode values live in `:root` and map to Tailwind semantic color utilities. This small indirection keeps component markup stable if a complete theme is introduced later.

### Tailwind defaults over parallel scales

The default spacing, breakpoints, typography scale, maximum-width utility, and radius utility already represent the approved design. Duplicating them as custom tokens would add vocabulary without adding capability.

### Components follow real use cases

Energy Insights does not adopt a large component library during the foundation phase. Shared UI components will be introduced when actual product features establish repeated visual and behavioral requirements.
